## 1. Journey & step-sequencing audit (the core new work)

Current module order (`ALL_MODULE_IDS`): product-selection → supplier-sourcing → common-documentation → compliance-by-product → channel-launch → ads-growth → tracking-analytics.

### 1.1 CONFIRMED BUG — product-selection module (user-flagged)

Source: `journey-rules.ts:101-115`, `step-details.ts:156-233`, `journey-graph.ts:64-67`.

Two required subtasks in module 1:
- `product-shortlist` → "**3 products** shortlisted with margin check"
- `samples-ordered` → "**Sample order placed**"

Two defects:

1. **Sample-before-supplier is impossible.** Supplier discovery is module 2 (`supplier-sourcing`). You cannot place a sample order in module 1 — you don't have a supplier yet. `step-details` doneCriteria even says "Each selected SKU has *supplier sample confirmation*" — a supplier artifact demanded a module early.
2. **"3 products" contradicts the app's own launch step.** `channel-launch` requires "First listing live (**1 hero SKU**)" and `step-details` says "Publish 1 hero listing first." So the app tells a beginner to validate 3, then launch 1. For the lean-budget beginner persona (Meesho, <₹20k, COD-first) the "one product at a time" discipline is the correct dropship playbook; "shortlist 3 SKUs" is an inventory/FBA-brand mindset that burns a lean beginner's sample + ad budget 3×.

**Fix:**
- Module 1 `product-selection` becomes **find & validate ONE hero product** (keep a 2-item backup bench, not a 3-SKU launch set). Reframe `product-shortlist` → "1 hero product chosen, margin-checked (2 backups noted)". doneCriteria drops "exactly 3 launch SKUs."
- **Move `samples-ordered` out of module 1 into `supplier-sourcing`** (module 2), after `supplier-vetted`. Sample ordering is a supplier action. Its `why` ("catch quality before inventory commitment") belongs exactly there.
- Note: `samples-ordered` is referenced by milestones/crisis lookups (`journey-graph.ts` legacy `MODULE_SUB_TASKS`, milestones.ts). Moving module ownership must update: `journey-rules.ts` (BASE_SUBTASK_RULES), `journey-graph.ts` MODULE_SUB_TASKS, `step-details.ts` (both module blocks), any milestone referencing it, and tests.

## 3. LLM / agentic personalization (biggest new lever)

### 3.1 The gap
We collect 10 structured fields (`onboarding-steps.ts`) but personalize via hardcoded `switch(moduleId)` templates. Two different users with the same `productType` get near-identical text. The profile is rich enough to justify a real generative layer.

### 3.2 Recommended architecture — **template-anchored generation** (not free-form)

Do **not** let an LLM free-write the plan (hallucination risk on GST/fees is a legal liability for a "correct numbers" brand). Instead:

1. **Deterministic core stays deterministic.** All numbers (fees, RTO, GST deadlines, HSN) come from our engines/data, never the LLM.
2. **LLM personalizes the *narrative + prioritization + sequencing rationale*** around that fixed core: given `{profile + derived facts + the module's factual checklist}`, produce (a) a personalized plain-language plan summary, (b) ordering/priority of the pre-defined subtasks with reasons, (c) persona-specific "watch-outs." Output is **structured JSON constrained to reference only IDs/values we passed in** — the model rewrites/prioritizes, it does not invent facts.
3. **Fill the existing template with LLM output.** `StepDetail` shape stays; LLM fills `plainLanguageSummary`, orders `actionChecklist`, writes `mistakesToAvoid` in the user's context. Falls back to current static templates if the LLM call fails or user is on a plan without it.

### 3.3 Where it runs
- **Generate once, at plan-finalization** (after onboarding + product decision), not per page-load. Store the generated plan JSON in a `journey_plan` row keyed by profile. Regenerate only on material profile change (product/channel/state/GST status). This caps cost at ~1 generation per user per meaningful change, not per session.
- Model: use latest cost-appropriate Claude (Haiku-class for cost, Opus/Sonnet for the one-time deep plan). One deep generation per user ≈ negligible per-user cost; the cap is the storage of the generated JSON (small, text).

### 3.4 Gating & cost control
- LLM plan = a **Starter+ feature** (it's the paid "mentor" moment). Free Scout stays on static templates. This also aligns cost with revenue.
- Hard cap: N regenerations/month per plan (e.g. Starter 5, Growth 20) — profile thrash protection.
- Prompt-injection surface: profile fields are user-supplied free-ish text (state is a dropdown, but product notes could be free text later). Never let profile text alter system instructions; treat as data.

### 3.5 Agentic (later, optional)
A true "agent" (tools: fee engine, GST calendar, web lookup) is overkill now and adds failure modes. The template-anchored generation above delivers 90% of the perceived value with 10% of the risk. Revisit agents only for the post-launch "weekly review" narrative once base is proven.

## 4. Pricing, infra cost & data caps

### 4.1 Current state
- Tiers: Scout ₹0 / Starter ₹49(₹399yr) / Growth ₹199(₹1,599yr) — approved, shipped.
- Caps today: profiles 1/2/5, recon 0/1/∞, crisis protocols, digest, rate alerts.
- **No storage or data-volume cap anywhere.** `entitlements.ts` has no bytes/row limits.

### 4.2 Infra cost reality (the user's question)
Cost drivers for this stack:
- **Supabase**: free tier 500MB DB + 1GB file storage; Pro $25/mo = 8GB DB + 100GB storage. The growth vector is **payout-reconciliation CSV uploads** (Growth = unlimited recon) + generated LLM plan JSON + settlement history trends.
- **Vercel**: bandwidth + function invocations; LLM calls if proxied through our functions add compute time.
- **LLM**: per-generation token cost (bounded by §3.3/§3.4 caps).
- **Domain/email (Resend)**: fixed/negligible.

At ₹49–199/mo (~$0.6–2.4), gross margin is fine **until** a Growth user with "unlimited recon + history" stores hundreds of MB of CSVs. Unbounded "unlimited" is the risk.

### 4.3 Recommended caps (add a storage dimension to `Entitlements`)
Add to `Entitlements`:
- `maxStoredReconUploads` (retention window, not truly infinite): Starter 3 months history, Growth 12 months, then auto-archive/purge oldest. "Unlimited" in marketing = "we keep 12 months of history" in reality — honest and cost-bounded.
- `maxUploadSizeMB` per file (e.g. 5MB) — a settlement CSV is tiny; caps abuse.
- `llmPlanRegensPerMonth` (per §3.4).
- Purge job: recon rows older than retention window → delete raw CSV, keep the derived summary numbers (cheap, and keeps the "history trend" value without storing source files forever).

This changes "unlimited" claims to "unlimited reconciliations, 12-month history" — a defensible, cost-safe promise. Update pricing copy accordingly (avoids a future "you said unlimited" complaint — §5).

### 4.4 Pricing structure — keep, with two tweaks
- Keep ₹49/₹199 (validated against Shiprocket anchor).
- **Add the LLM personalized plan as the headline Starter feature** — it's the concrete "why pay ₹49" moment better than "full journey."
- Consider a **one-time ₹99 "Launch Pack"** (CA-consult referral + photography checklist review) to monetize pre-revenue users who won't subscribe — prior review already suggested this; still open.

## 6. Engagement / fun / aesthetic (make them not regret paying)

Design system (Mono Depth) is strong and distinctive — do not add color/decoration; work within it. Engagement levers, ranked by impact/effort:

1. **Make the simulators a retention loop, not one-shot.** COD-call / NDR / sourcing-swipe are the app's most novel assets. Add: streak on daily "one rehearsal," a score history, and a "graduation" badge. Cheap, high delight, on-brand (mono badges).
2. **Personalized plan reveal moment** (§3) — a generated "your route" that feels written for them is the single biggest "worth it" spike. Present it as a cinematic reveal (Mono Depth reveal animation already in the motion budget).
3. **Progress as narrative, not %.** "From first doubt to first payout" is the tagline — instrument milestones as named checkpoints ("Docs armored", "First listing live", "First payout") with a mono milestone stamp, not a bare progress ring. Milestones lib already exists.
4. **Weekly ritual** (shipped 3.2) — lean into it as the habit engine: the Monday digest is the retention core for post-payout users. Make its in-app card feel like a "coach's note."
5. **Loss-aversion framing in tools** — the calculators already show "advertised vs actual"; surface a running "₹ this tool saved/caught you" tally per profile. Concrete ROI = renewal justification.
6. **Micro-wins in onboarding** — the ack lines are good; add a first "aha" (margin calc on their product) inside onboarding before asking for signup/payment (2-min time-to-value is our conversion edge per pricing doc).

Aesthetic: no changes to the system; the wins are motion-timed reveals on the plan + milestone stamps, both already within DESIGN_SYSTEM.md's allowed motion.
